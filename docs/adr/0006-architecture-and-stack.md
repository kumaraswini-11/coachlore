# 6. Architecture and stack

- Status: Proposed. Accepted piece by piece by the owner; each accepted
  piece goes into AGENTS.md's Stack list.
- Date: 2026-10-21

## Context

The [project doc](../project-doc.md) fixes what Coachlore v1 does and how it
behaves ("How it works"); [the specs](../specs/README.md) order the work.
This record decides what it's built with and how the parts fit.

Three rules shape every choice:

- **Nothing before it's needed.** A piece is chosen here, but it's added to
  the repository by the first spec that needs it, not before. The table
  below names that spec. A piece with no spec that needs it isn't chosen.
- **$0 to run while it's small** (the project doc). Where that has a real
  cost or risk, it's said, with what would make us switch.
- **The core is framework-agnostic** (AGENTS.md): the Pokémon data model,
  the league rules and the battle-log parser are plain TypeScript packages.

Versions are the newest release at least two weeks old on the day each
piece is added (AGENTS.md, "Versions"); the versions below are what that
was on 2026-10-21, to show each is a stable, maintained line.

### The shape

| `packages/battle-log` | The battle-log parser: a replay's log in, the score, KOs and faints out. No framework.                                                                                                               | 009      |

**One server, not four.** The research proposed separate API, worker and
bot apps with Redis between them. For one league of 8–16 coaches on one
VM, one process does all of it with fewer moving parts: jobs run in it
from a queue in PostgreSQL, the bot needs no long-lived connection (it
receives commands over HTTP and posts over Discord's REST API), and one
Socket.IO server needs no Redis adapter. The jobs are split into their own
process, from the same code, when job work is seen to slow the draft room;
Redis is added when there's a second server.

**The Dex doesn't depend on the server.** Its pages are generated from the
dataset at build time and served from the CDN, so the Dex is fast, works
offline, and stays up if the VM is down. The server reads the same
dataset (`packages/dex`) to know which forms exist for tier lists, rosters
and battle logs.

**The database and sign-in are packages of their own**, so each can be
swapped without touching the server's features: Turborepo's guide
integrates the ORM "as a shared database package in your Turborepo
monorepo" ([Prisma guide](https://turborepo.dev/docs/guides/tools/prisma),
bundled with the installed version), and Better Auth shares its types with
the client "For Monorepo or Single-Project Setups"
([TypeScript](https://www.better-auth.com/docs/concepts/typescript)). The
web app uses `packages/auth`'s client; seed and migration scripts use
`packages/db`. **The AI stays inside the server**, its only user, behind one
interface (AGENTS.md: "Code moves into a shared package when a second
package needs it").

## The owner's calls

1. **A domain: none for now** (the owner, 2026-10-21). The design above
   works without one; buying one later changes two addresses, not the code.
2. **The AI provider**, before spec 012. Recommended: Groq's free tier, for
   its no-retention default; Gemini's free tier excludes users in the EEA,
   Switzerland and the UK.
3. **Oracle's card and Pay As You Go.** Upgrading avoids idle reclamation
   and capacity limits, by community reports rather than Oracle's docs, but
   exposes the card to charges beyond the free allowance. Recommended: stay
   on the free account, size the VM as above, and move to Hetzner if Oracle
   reclaims it.
4. **Where PostgreSQL runs**, before spec 006. Recommended: on the VM, as
   above; Neon when the free plan fits or a paid one is chosen, by changing
   `DATABASE_URL`.

## Alternatives considered

- **Separate API, worker and bot apps with Redis** (the research's plan):
  more to deploy and watch, with nothing at v1's size that needs it.
- **Everything in Next.js on Vercel**: no long-lived process for the draft
  room or jobs; Vercel's WebSockets are a beta capped at 300 seconds on
  Hobby.
- **A managed PostgreSQL free tier**: each one sleeps, pauses or expires.

## Consequences

- Until spec 006, Coachlore runs on Vercel alone, at $0, with no server.
- From 006: a free DuckDNS name, an Oracle VM with Coolify, PostgreSQL with backups
  off the VM, and Sentry for the server.
- Each piece above is added with its spec, at the newest version at least
  two weeks old that day, and recorded in AGENTS.md's Stack list when the
  owner accepts it.
- Triggers to revisit: a second server (Redis and Socket.IO's Redis
  adapter); job work slowing the draft room (a separate job process);
  Sentry's free limits reached (OpenTelemetry and Grafana); a commercial
  turn (Vercel Pro or the web app on the VM, and a paid AI tier).
